# reSpeaker XVF3800 firmware (LiveKit ESP32 client)

The XVF3800 hardware is a two-chip system:

- **XMOS XU316** — 4-mic array processing: acoustic echo cancellation, noise
  suppression, beamforming. It hands the ESP32 a clean, full-duplex audio
  stream (I2S). Stock DSP firmware works as-is; see Seeed's
  [XVF3800 wiki](https://wiki.seeedstudio.com/respeaker_xvf3800_introduction/)
  if you ever need to reflash it.
- **XIAO ESP32-S3** — runs the network stack. Seeed's stock firmware targets
  **Agora/TEN framework** and cannot talk to LiveKit, so we flash our own
  firmware built on the official
  [livekit/client-sdk-esp32](https://github.com/livekit/client-sdk-esp32) SDK
  (developer preview, distributed via the Espressif Component Registry;
  ESP-IDF ≥ 5.4; ESP32-S3, bidirectional Opus audio with AEC on the XMOS).

The SDK's examples (`voice_agent`, `minimal`, `minimal_video`) live under
`components/livekit/examples/` in the repository; start from
**`voice_agent`** (bidirectional voice chat with an AI agent). The XVF3800 is
not in the example's built-in board list — a custom codec-board entry is
covered in §3.1 below.

> The LiveKit ESP32 SDK docs are the source of truth for configuration keys —
> the exact Kconfig symbol names below may differ slightly per release.

## 1. Install ESP-IDF (5.4/5.5 line — not 6.x)

Follow https://docs.espressif.com/projects/esp-idf/en/v5.4/esp32s3/get-started/
(Linux: `install.sh esp32s3`, then `. ./export.sh`). Use a 5.x release — the
latest v5.5.x (v5.5.5 at the time of writing) is a good choice. **ESP-IDF 6.x
does not work with this stack**: 6.x removed IDF's `json` component (still
present through v5.5.x) while the audio stack (`espressif/esp-sr`, pulled in
via `esp_capture`'s AEC source) still requires it, so configure fails with
`Failed to resolve component 'json' required by component
'espressif__esp-sr': unknown name`. Multiple IDF versions can coexist (e.g.
`~/esp/esp-idf-v5.5` activated with its own `export.sh`) — just make sure the
shell you run `idf.py` in sources the 5.x environment (`idf.py --version`).

## 2. Create the voice-agent firmware project

The SDK is distributed through the Espressif Component Registry — cloning the
SDK repo is optional. Run this **outside this repository** (it creates a
`voice_agent/` project directory) with the ESP-IDF environment active:

```bash
idf.py create-project-from-example "livekit/livekit=0.3.2:voice_agent"
cd voice_agent
idf.py set-target esp32s3   # REQUIRED - never build before this, see below
```

> **Never skip `idf.py set-target esp32s3` — and never run `idf.py build`
> before it.** New ESP-IDF projects default to the classic **ESP32** target,
> but `livekit/livekit` is only published for **ESP32-S3 and ESP32-P4** (and
> the example's board components, e.g. `espressif/esp32_s3_korvo_2`, are
> S3-only). A build with the default target therefore dies during dependency
> resolution with `Version solving failed: no versions of livekit/livekit
> match <ver>` / `has suitable versions for other targets: esp32s3` — "no
> versions match" means *not published for this target*, not that the version
> is missing. `set-target` rewrites `sdkconfig` and wipes `build/`, so run it
> before `menuconfig` (re-apply the §3 settings if you had already
> configured). Sanity check in the build output:
> `xtensa-esp32s3-elf-gcc` and `Building ESP-IDF components for target
> esp32s3` = good; `xtensa-esp32-elf-gcc` / `target esp32` = this step was
> skipped.

> The `=0.3.2` pin keeps builds reproducible. Omit it and the project is
> created from the **latest** release (0.3.10 at the time of writing); the
> generated project pins exactly what it was created from in
> `main/idf_component.yml` — check there if unsure. This guide and the
> wake-word overlay (`firmware/`) were validated against `0.3.2`; newer
> releases are fine target-wise but may drift in the files the overlay
> patches.

> The SDK is in developer preview and its layout has changed before: the
> examples now live under `components/livekit/examples/` in the repository
> (the old top-level `examples/voice_agent` path no longer exists). To browse
> or patch SDK sources, clone the repo and work from that path; the registry
> version above is pinned, so builds stay reproducible.

(Connect the XIAO ESP32-S3 to the XVF3800 carrier board first; the XIAO must
be mounted on the reSpeaker board so it can reach the XMOS over I2S.)

## 3. Configure

Configure via the **"LiveKit Example"** menu (`idf.py menuconfig`) or by
editing `sdkconfig` directly. For this stack:

```ini
# WiFi
CONFIG_LK_EXAMPLE_USE_WIFI=y
CONFIG_LK_EXAMPLE_WIFI_SSID="<your SSID>"
CONFIG_LK_EXAMPLE_WIFI_PASSWORD="<your password>"
# Talk to OUR LiveKit server (not the LiveKit Cloud sandbox)
CONFIG_LK_EXAMPLE_USE_PREGENERATED=y
CONFIG_LK_EXAMPLE_SERVER_URL="ws://<host-LAN-IP>:7880"
CONFIG_LK_EXAMPLE_TOKEN="<output of the mint command below>"
# Custom XVF3800 board entry added in §3.1
CONFIG_LK_EXAMPLE_CODEC_BOARD_TYPE="XVF3800"
# Console via USB Serial/JTAG: frees GPIO43/44 (the XMOS I2S data pins, §3.1),
# which the default UART console otherwise occupies
CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y
```

> Run `idf.py` from a plain shell in the project root. If the project contains
> a `CMakePresets.json` (IDE integrations such as the ESP-IDF or CMake Tools
> VS Code extension drop one in), idf.py 6.x picks it up ("CMake presets file
> found but no preset name given...") and configures into its `binaryDir`
> **without expanding** the standard `${sourceDir}`/`${presetName}` macros —
> configure then fails on paths like
> `.../voice_agent/${sourceDir}/out/build/${presetName}` and a missing
> `toolchain-esp32.cmake`. Unless you build from the IDE, move the file aside
> (`mv CMakePresets.json CMakePresets.json.bak`), delete the leftover
> `${sourceDir}` directory, and re-run `idf.py set-target esp32s3`.

> The example also offers a LiveKit Cloud sandbox mode
> (`CONFIG_LK_EXAMPLE_USE_SANDBOX`) with its own hosted demo agent — ignore
> it. This stack provides the agent; the example's bundled `agent/` folder is
> not needed. Tokens expire — mint a long-lived one for the device (below).

### 3.1 XVF3800 codec-board entry (required once per project)

The example plays/captures audio through Espressif's `codec_board` component,
which only knows a fixed list of dev boards — the XVF3800 is not among them.
Add a custom entry to
`managed_components/tempotian__codec_board/board_cfg.txt` (the directory is
created when the registry dependencies are first downloaded — i.e. by
`idf.py set-target esp32s3` in §2 or the first build; re-apply the edit if
you ever delete `managed_components`):

```text
Board: XVF3800
i2c: {sda: 5, scl: 6}
i2s: {mclk: -1, bclk: 8, ws: 7, din: 43, dout: 44}
out: {codec: DUMMY, use_mclk: 0}
in: {codec: DUMMY}
```

Pins per the XVF3800 schematic and Seeed's own XIAO client (the Agora/TEN
framework guide's `get_i2s_pins()` / `get_i2c_pins()`): the XMOS XVF3800
handles mics, AEC and the TLV320AIC3104 speaker codec; the ESP32-S3 only
exchanges 2-channel I2S audio with it (WS = GPIO7, BCLK = GPIO8,
DIN = GPIO43, DOUT = GPIO44) and reaches it over I2C (SDA = GPIO5,
SCL = GPIO6). **MCLK stays disabled** (`mclk: -1`, `use_mclk: 0`): Seeed's
working client runs with `mck_io_num = -1` — the XMOS I2S firmware does not
want a host MCLK on this carrier. The ESP32 is still the I2S master (drives
BCLK + WS). This board_cfg entry is the codec_board equivalent of the
`get_i2s_pins()` / `get_i2c_pins()` modification in Seeed's Agora/TEN guide
- that project's audio stack is ESP-ADF, where the pins live in the ADF
board driver; in our build the pins are data in `board_cfg.txt`. `DUMMY`
codec means the ESP32 configures no codec chip itself — if the speaker
stays silent, the AIC3104 needs explicit I2C setup per Seeed's wiki.

> **`board_cfg.txt` is embedded into the firmware at build time, and
> `managed_components/` regenerates whenever dependencies are re-resolved** —
> a fresh project, a deleted `managed_components/` directory or a component
> version bump silently drops this edit. Verify it before every build:
> `grep -A4 XVF3800 managed_components/tempotian__codec_board/board_cfg.txt`.
> Without the entry the boot fails with `CODEC_INIT: No codec device found`
> → `Capturer must be set for media publishing` → `Failed to create room`.
> Rebuild (`idf.py build`) after any edit to the file.

Quick re-apply when the entry is missing (run from the project root):

```bash
cat >> managed_components/tempotian__codec_board/board_cfg.txt <<'EOF'

Board: XVF3800
i2c: {sda: 5, scl: 6}
i2s: {mclk: -1, bclk: 8, ws: 7, din: 43, dout: 44}
out: {codec: DUMMY, use_mclk: 0}
in: {codec: DUMMY}
EOF
grep -A4 XVF3800 managed_components/tempotian__codec_board/board_cfg.txt
idf.py build
```

Mint the device token from the server host:

```bash
cd /opt/src/voice-assistant
docker compose run --rm agent python /app/scripts/mint_token.py \
    --identity respeaker-1 --room home --name "reSpeaker" \
    --ws-url ws://<host-LAN-IP>:7880 --valid-hours 8760
# paste the JWT into menuconfig (or into the token source file, per example docs)
```

Tip: long-lived token (`--valid-hours 8760`) for the device; treat it like a
password. Room `home` is the default conversation room.

### 3.2 Patch the example's board init (required once per project)

The example's `main/board.c` unconditionally initializes the Korvo-2 BSP
(`bsp_i2c_init()` + `bsp_leds_init()`), which probes a TCA9554 I/O expander
that only exists on the Korvo board — on the XVF3800 that assert kills the
boot right after flashing:

```
assert failed: bsp_leds_init esp32_s3_korvo_2.c:623 (bsp_io_expander_init())
```

This runs *before* `set_codec_board_type()`, so no menuconfig setting can
avoid it. Replace `main/board.c` with the patched version from this
repository (same `$VA` as in §6):

```bash
cp "$VA/firmware/main/board.c" main/board.c
```

The patch guards the two BSP calls behind
`strcmp(CONFIG_LK_EXAMPLE_CODEC_BOARD_TYPE, "XVF3800") != 0`, keeps
everything else (temperature sensor, codec init, `get_cpu_temp` RPC), and —
ported from Seeed's own Agora/TEN XIAO client — initializes the AIC3104
speaker codec over I2C (the DAC outputs are muted at power-on; without this
the speaker stays silent even with audio flowing). The Korvo `set_led_state`
RPC has no LEDs to drive on this board (the XVF3800's LEDs hang off the
XMOS — a later project, see `firmware/README.md`).

## 4. Build & flash

```bash
idf.py build
# put the XIAO ESP32-S3 into bootloader if needed (hold BOOT, tap RESET),
# find its serial port (often /dev/ttyACM0), then:
idf.py -p /dev/ttyACM0 flash monitor
```

You should see it join WiFi and connect to the LiveKit room; the agent joins
automatically and speaks the greeting through the XVF3800's speaker output.

## 5. Verify & iterate

- Server side: `docker compose logs -f agent` shows `joining room home`.
- Talk: *"what time is it?"*, *"set a 5 minute timer"* — full-duplex works
  (you can interrupt the agent; the XMOS AEC cancels its echo).
- The agent also publishes data messages (topic `assistant.event`, e.g. timer
  expiry) which the firmware can use for LEDs/UI — see
  `client-sdk-esp32` data-stream APIs.

## 6. Wake word overlay (ESP-SR WakeNet, connected standby)

The firmware can be extended with an Echo-style on-device wake word using the
overlay in this repository (`firmware/`): the device stays in the LiveKit room,
but publishes only silence until the wake word is heard. Full behavior, tuning
and troubleshooting: **`firmware/README.md`**.

Apply it after §2/§3 (ESP-IDF environment active):

```bash
cd voice_agent
VA=/opt/src/voice-assistant   # path of this repository on your machine
cp -r "$VA/firmware/main/." main/
cp "$VA/firmware/partitions.csv" .
cat "$VA/firmware/sdkconfig.defaults.wakeword" >> sdkconfig.defaults
rm -f sdkconfig && idf.py set-target esp32s3 && idf.py menuconfig
```

**Required SDK component patches** (the overlay cannot reach these files):

1. **Signaling buffer** - `components/livekit/core/signaling.c`: raise
   `SIGNAL_WS_BUFFER_SIZE` from `20 * 1024` to `64 * 1024` (or larger) - the
   `JoinResponse` exceeds the stock 20 KB once the agent participant is in the
   room, and the 0.3.2 handler does not reassemble fragmented WebSocket
   messages (see Troubleshooting).
2. **Engine task stack** - `components/livekit/core/engine.c`: in the
   `xTaskCreate(engine_task, "engine_task", 4096, ...)` call raise the stack
   to `12288`. Once the join decodes fully and streaming starts, the engine
   task also drives the wake-word model re-init on capture open - deeper than
   the stock 4 KB budget. Symptom if skipped:
   `***ERROR*** A stack overflow in task engine_task has been detected.`
   right after `DTLS: Init SRTP OK`.
3. **I2S slot width: keep the stock 16-bit slots** - do NOT force 32-bit
   slots in `managed_components/espressif__esp_codec_dev/.../audio_codec_data_i2s.c`
   (the file logging as `I2S_IF`). Hardware-verified on the XVF3800: with the
   stock 16-bit slots the XMOS delivers real speech (loud bursts,
   rms > 1000); with `slot_bits = 32` forced in `set_drv_fs()` the capture
   goes all-zero. The XMOS's I2S slave tolerates the ESP32's 16-bit slot
   timing but not the 32-bit variant (in that mode it outputs digital
   silence). The capture is bursty - real audio interleaved with XMOS-zeroed
   silence (its noise suppression zeroes non-speech) - which WakeNet
   tolerates.

Wake-word specifics on top of §3:

- **Flash size**: the overlay switches the project to 8 MB and adds an esp-sr
  `model` partition (`firmware/partitions.csv`) - required for `srmodels.bin`.
- **Wake word model**: menuconfig → *ESP Speech Recognition → Load Multiple
  Wake Words* (default `wn9_hilexin`, "Hi Lexin"; alternatives include
  `wn9_hiesp` "Hi ESP", `wn9_alexa`). Keep exactly one model enabled.
- **Behavior menu**: menuconfig → *Wake Word* (enable gate, pre-wake buffer,
  follow-up window, detection threshold, chime).
- **Build & flash**: `idf.py build && idf.py -p /dev/ttyACM0 flash monitor` -
  esp-sr's build automatically adds `build/srmodels/srmodels.bin` to the flash
  step.
- **Verify**: on boot, `wake_word: WakeNet 'wn9_hilexin' ready: phrase
  "Hi Lexin"` then `wake_word: Gating armed`; say the wake phrase → chime +
  `wake_word: Wake word detected (...), going active`; after ~10 s of quiet →
  `re-arming`. While armed the agent receives no audible audio.
- The XIAO ESP32-S3's 8 MB PSRAM holds the model and the pre-wake buffer; the
  SDK's `show_threads()` (see the SDK README) plus `docker compose logs -f
  agent` on the server side are the quickest health checks.
- **Wi-Fi tuning**: the overlay's `main.c` keeps the radio always on
  (`esp_wifi_set_ps(WIFI_PS_NONE)`; the overlay's
  `sdkconfig.defaults.wakeword` also sets
  `CONFIG_ESP_WIFI_POWER_SAVE_NONE=y`) and caps TX power at 8.5 dBm
  (`esp_wifi_set_max_tx_power(34)`) to reduce RF interference with the audio
  path. Only apply the TX cap with good RSSI (> -70 dBm) - it cuts range.
  Verify: the boot line `wifi:pm start` disappears when power save is off.

Stock models are English/Chinese; custom phrases (e.g. German) need
Espressif's WakeNet customization service, a microWakeWord model, or LiveKit's
[`livekit-wakeword`](https://github.com/livekit/livekit-wakeword) models once
they run on ESP32 (the engine interface `firmware/main/wake_word_engine.h` is
swappable). See `firmware/README.md` and `docs/architecture.md`.

## Troubleshooting

| Symptom | Fix |
|---|---|
| Build dies in dependency resolution: `Version solving failed: no versions of livekit/livekit match <ver>` and/or `has suitable versions for other targets: esp32s3` (log shows `target esp32`, `xtensa-esp32-elf-gcc`) | the project is still on ESP-IDF's default ESP32 target — run `idf.py set-target esp32s3` (§2), re-apply §3 in menuconfig, rebuild. Harmless noise in the same log: the CMake `Compatibility with CMake < 3.10` warning (the example pins `cmake_minimum_required(VERSION 3.5)`) and `Could not use 'git describe'` (project is not a git repo) |
| Configure fails: `Failed to resolve component 'json' required by component 'espressif__esp-sr': unknown name` (or other ESP-IDF 6.x breakage) | you are on ESP-IDF 6.x, which removed IDF's `json` component (still present in v5.5.x) that the audio stack (`esp-sr`) requires — install ESP-IDF 5.5.x, activate it (its `export.sh`), then in the project run `rm -rf build sdkconfig dependencies.lock managed_components` and `idf.py set-target esp32s3` again. The component declares `idf >= 5.4` with no upper bound, so 6.x resolves during dependency solving but does not build |
| `idf.py` announces `CMake presets file found but no preset name given` and configure fails with literal `${sourceDir}/out/build/${presetName}` paths or missing `toolchain-esp32.cmake` | a `CMakePresets.json` (usually IDE-generated, e.g. by the ESP-IDF/CMake Tools VS Code extension) is intercepting idf.py, which does not expand its macros — `mv CMakePresets.json CMakePresets.json.bak`, `rm -rf '${sourceDir}'` (literal directory name!), re-run `idf.py set-target esp32s3`; keep the plain CLI flow unless you build from the IDE |
| Boot halts after flash: `assert failed: bsp_leds_init esp32_s3_korvo_2.c:623 (bsp_io_expander_init())` | the stock example's `main/board.c` initializes the Korvo-2 BSP unconditionally — apply the §3.2 `board.c` patch, rebuild, reflash |
| Device boots and joins the room, but captured/played audio is garbled or silent | the stock `codec_init_cfg` in `main/board.c` is Korvo-shaped (`.in_mode = CODEC_I2S_MODE_TDM`, `.in_use_tdm = true`, for the ES7210 mic array); the XVF3800's XMOS exchanges 2-ch I2S — if needed switch to the standard-I2S mode (enum in `managed_components/tempotian__codec_board/include/codec_init.h`) with `.in_use_tdm = false` and retest |
| Boot log: `CODEC_INIT: No codec device found`, then `Failed to get record/render device handle`, `Capturer must be set for media publishing`, `Failed to create room` | the §3.1 XVF3800 entry is missing from *this* project's `managed_components/tempotian__codec_board/board_cfg.txt` — `managed_components/` regenerates whenever dependencies re-resolve (fresh project, deleted directory, component bump) and silently drops the edit. Re-add the entry (§3.1), verify with `grep -A4 XVF3800 managed_components/tempotian__codec_board/board_cfg.txt`, rebuild, reflash. Also confirm `grep CONFIG_LK_EXAMPLE_CODEC_BOARD_TYPE sdkconfig` shows exactly `"XVF3800"` |
| Boot log: `GPIO 44 and 43 are used as console UART I/O pins` | the default UART console occupies GPIO43/44 — the XVF3800's I2S **data** pins (§3.1). Switch the console to USB: menuconfig → *ESP System Settings → Channel for console output → USB Serial/JTAG Controller* (`CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y`), rebuild, reflash — logs keep coming over the same USB port |
| Room shows `Connected` but the log contains scary lines (`Failed to decode signal res: type=16/9`, `Not found for bind remote ...`, ICE candidates for `127.0.0.1` / `172.17.x` / public srflx IPs, `MODEL_LOADER: Can not find model in partition table`, `wakenet model not found`) | all benign at this stage: the 0.3.x client skips signaling messages it doesn't implement; the ICE agent logs incoming checks before registering the matching pair; the server advertises extra candidates (docker bridges, loopback for the port-forward test flow, public STUN reflexive) that lose the election to the LAN pair; and the esp-sr `model` partition only exists after the §6 wake-word overlay — until then the AEC source runs the built-in low-cost AEC (`AFE Pipeline: ... AEC(SR_LOW_COST)`) |
| Signaling connects, then `***ERROR*** A stack overflow in task engine_task has been detected` right after `DTLS: Init SRTP OK` (device reboots in a loop) | the join now decodes fully (WS buffer fixed) and streaming start + the wake-word model re-init run deeper than the SDK's 4 KB `engine_task` stack - in `components/livekit/core/engine.c` raise the `xTaskCreate(engine_task, "engine_task", 4096, ...)` stack size to `12288`, rebuild, reflash (see §6) |
| Room `Connected`, but `mic tap:` shows alternating all-zero and signal seconds, `AFE: Ringbuffer of AFE(FEED) is full` warnings and `DTLS: mbedtls_ssl_read error` | the capture pipeline is stalling: (1) check WiFi - real-time audio needs RSSI better than ~-70 dBm (boot log `rssi:` value); at -89 the network stalls back up the whole pipeline; (2) halve the DSP load by disabling the AEC source's *internal* WakeNet - the overlay's standalone engine already detects. Depending on the component version the knob is `wakenet_init = false` or a `wakenet_model_name` assignment: locate it with `grep -rni wakenet managed_components/ | grep -v '\\.h:'` and neutralize it (set to `false`/`NULL`) in the AEC source, then rebuild. Keep `MIC_LEVEL_TAP` on until the tap shows continuous non-zero levels while speaking |
| Signaling connects, then `Failed to decode signal res: type=1, error=parent stream too short` (often followed by e.g. `type=8/13, wrong/invalid wire type`), ~60 s of silence, `Connection reset by peer`, `Failure reason: Join Incomplete` | the server's `JoinResponse` exceeds the SDK's signaling WebSocket buffer and arrives in fragments (`type=1` = `join` in the SDK's proto; later chunks get misread as other types). The 0.3.2 `WEBSOCKET_EVENT_DATA` handler has **no reassembly** - every fragment is decoded independently (upstream: livekit/client-sdk-esp32#86). Fix: in `components/livekit/core/signaling.c` raise `#define SIGNAL_WS_BUFFER_SIZE` (20 KB stock) to `64 * 1024`; if the errors persist, the payload is even bigger - go to `128 * 1024` or `256 * 1024` (the buffer is heap-allocated and lands in PSRAM with the default sdkconfig). Verify the edit is in the file the build actually uses (`grep -rn SIGNAL_WS_BUFFER_SIZE .` from the project root) and do a clean rebuild. Also note the buffer must exceed the *largest* signaling message - with the agent in the room the join grows over time |
| Device never shows up in the room / agent logs at all (agent only logs other participants like `web-1`) | read the *device* serial log (`idf.py -p /dev/ttyACM0 monitor`) — WiFi `got ip` present? then check the connect config: `grep CONFIG_LK_EXAMPLE_USE sdkconfig` must show `CONFIG_LK_EXAMPLE_USE_PREGENERATED=y` (the example's `sdkconfig.defaults` ships **sandbox** mode!), URL must be the host's **LAN IP** (`ws://<host-LAN-IP>:7880`, never localhost), the token must be minted with the *current* `LIVEKIT_API_SECRET` (`make token ID=respeaker-1 ROOM=home`), and `NODE_IP` in `.env` must be empty (or the LAN IP) for LAN use |
| Agent log spams `Error predicting end of turn ... no inference executor` and warns about `turn_handling=TurnHandlingOptions` (browser sessions affected too) | server-side, not device-related: the running agent image is older than the repo's `livekit-agents==1.5.17` pin (1.6+ moved turn-detector inference into `livekit-local-inference`, which needs an x86-64-v2 CPU) — rebuild and recreate it: `make restart-agent`, then verify `docker compose exec agent python -c "import livekit.agents; print(livekit.agents.__version__)"` → `1.5.17`. Non-fatal either way (sessions fall back to VAD endpointing); `ENABLE_TURN_DETECTOR=false` silences it if you intentionally stay on a newer image |
| Connect fails w/ 401 | token room/identity mismatch, or `LIVEKIT_API_SECRET` changed after minting |
| Connect fails w/ timeout | server unreachable: check `ws://` host IP, firewall (TCP 7880, UDP 50000-50200) |
| No audio captured | check the XVF3800 board entry in §3.1 (I2S pins per Seeed's schematic) and that the XMOS runs its stock I2S-capable DSP firmware |
| Echo of the agent's own voice | ensure the XMOS AEC path is used (don't bypass the XVF3800 DSP) |
| Random disconnects when a participant leaves | known SDK issue in the 0.3.x developer preview (see the SDK README) — update the component version |
